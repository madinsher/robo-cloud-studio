# Post processors, program importers and ROS 2 packages

## Built-in posts = RoboDK's own posts, token for token

`src/posts/` re-implements RoboDK's post processors on a common `RoboPost` base (`robopost.ts`) that mirrors RoboDK's
`RobotPost` callbacks (`ProgStart`, `MoveJ`, `MoveL`, `MoveC`, `setFrame`, `setTool`, `setSpeed*`, `setZoneData`,
`setDO`, `waitDI`, `RunCode`, `RunMessage`, `ProgFinish`, `ProgSave`). A compiled program (`compileForPost`) is
replayed exactly the way RoboDK feeds its posts, so the output can be compared with RoboDK's line by line.

**Ground truth** (`tests/fixtures/posts_gt/`): `gen_gt.py` runs RoboDK's ORIGINAL posts (the compiled `libspp` /
`vXY` modules of `C:/RoboDK/Posts`) under RoboDK's embedded Python 3.10 through `python/post_shim.py` (RoboDK.exe is
never started, `Robolink` is blocked) on frozen job files:

* `feature_<robot>`: one program with every instruction kind (frame, tool, speeds, rounding, MoveJ / MoveL / MoveC,
  per-move overrides, numbered and named IO, waits with timeout, pause, comment, message, calls with and without
  arguments, raw code, sub-program, gripper event, stop) on 12 Library robots;
* `synth_misc_<robot>` (named / numbered frames and tools, long names, IO values) and `synth_split_<robot>` (program
  splitting with a lowered line limit);
* `lib_<station>__<program>`: 45 programs of 20 RoboDK Library stations, posted with the post RoboDK assigns to the
  robot.

`tests/posts_gt.test.ts` compares every file token by token (numbers within 1e-3; blank lines, dates and
"generated by" lines ignored): **153 / 153 cases equal for 27 RoboDK posts** (the 27 `feature_jt_<robot>` cases: moves
to joint targets, which RoboDK hands its posts with pose None): KUKA_KRC2, KUKA_KRC4, ABB_RAPID_IRC5,
ABB_RAPID_S4C, ABB_RAPID_OmniCore, Fanuc_R30i, Fanuc_RJ3, Motoman, Motoman_Cartesian, Universal_Robots,
Universal_Robots_URP (script + Polyscope `.urp` tree), Kawasaki, Comau_C5G, Mecademic, Staubli_VAL3 (project + split
libraries), CSV, Doosan_Robotics, Techman_TMscript, Denso_RC8, Epson_RC, Nachi_AX_FD, Mitsubishi, Dobot_V3, HCR
(JavaScript), JAKA (`.jks`), AUBO (`main.aubo`), Elite_Robots_EC_V3 (JBI with the Lua base conversion, RoboDK's
cumulative split parts and `M_<name>` caller). Regenerate with
`POSTS_GT_GEN=lib npx vitest run tests/posts_gt_gen.test.ts` then
`C:/RoboDK/Python-Embedded/python.exe tests/fixtures/posts_gt/gen_gt.py lib_`.

These cases feed the same compiled events to RoboDK's posts and to the studio's, so they check the posts only.
**Station → code** (the compilation of a station's programs into the calls RoboDK hands its posts, plus the post) is
checked against RoboDK 5.9.4's own `MakeProgram` of the Library stations: see the section below and its per-file table.

Deliberate deviations from RoboDK (its defects; normalised in `tests/posts_gt_util.ts`): with
`CompileOptions.nativeThreads` (control-model code generation, `src/ctl/codegen/vendor.ts`) a program started on a
thread runs in a URScript thread (RoboDK, and `compileForPost` by default, hand the bare name to the post as code);
Comau split parts close with their own names; Doosan
`wait_digital_input(...)` without the trailing `:`; Epson stop is `Pause` (RoboDK: `Wait -0.001`); call arguments
keep their commas (RoboDK writes `X(1,2)` as `X(12)` for Denso / Epson / Dobot / Comau); Mecademic circles are written
as linear moves along the arc (RoboDK drops them); Staubli split libraries get their `start/stop.pgx`. Not reproduced:
JAKA's Scratch `.zu` project (random ids), AUBO's `main.xml` tree (the executable `main.aubo` is), Omron TMflow zip
(password-protected by RoboDK; Omron robots use the TMscript post), RoboDK's Kinova post (the studio keeps its own
Kinova_Kortex post: RoboDK's embeds a 420-line driver class). Elite follows RoboDK exactly, including its defect that
IO, waits, calls and pauses run before the whole motion block: the post reports it as a problem.

Behaviour reverse-engineered with probe jobs through RoboDK's posts includes the UR blend rule (`# end trace` only for
code directly after a blended motion; unchanged speeds write nothing), Fanuc arc welding (`ArcStart` / `ArcEnd` become
`FINE Arc Start[11]` options of the previous motion + `Weave`), Motoman chained circles and the write order of clashing
truncated job names, Comau turn flags (`T1` = J4 turn, `T2` = J6 turn) and skipped duplicate linear targets, Nachi
smoothing levels (`SM = rounding / 25`), Mitsubishi structure flags (FL1 from the configuration, FL2 multi-turn
nibbles), Mecademic `StartProgram` numbering, Staubli configuration tracking and split rule.

Program names lose their blanks like in RoboDK (`Pick EarCup 1` -> `PickEarCup1`) for definitions and calls. Post
warnings (unsupported instructions, clashing file names) are added to the compiled program's `problems`.

## Station → code against RoboDK's MakeProgram

`tests/posts_library_code.test.ts` compares, file by file, what the studio writes for every program of the 57 Library
stations with what RoboDK 5.9.4 wrote itself (case-insensitive, numbers within 0.011, date / "generated by" lines
ignored; `tests/posts_library_util.ts`). There are two references, because RoboDK's output depends on whether the
station was updated before `MakeProgram`:

* **As loaded** (`tests/fixtures/posts_gt/library_loaded.tgz`, written by `tests/fixtures/posts_gt/dump_library_loaded.py`
  with RoboDK started on a free port 22500-22999 and closed after each station): `MakeProgram` of every program of the
  station as it is opened, together with RoboDK's intermediate post script (`Post<program>.py`: the exact `RobotPost`
  calls). Three comparisons per file: *events* (the studio's calls equal RoboDK's: joints, configurations, poses,
  frames, tools, speeds, calls; `src/posts/rdk_job.ts`), *post* (the studio's post run on RoboDK's own calls writes
  RoboDK's file) and *e2e* (`compileForPost` + the robot's post writes RoboDK's file). **218 of 226 compared files are
  equal in all three**; 12 programs have no reference because RoboDK did not return from `MakeProgram` within 10
  minutes (machining programs with the Mecademic / JAKA / Motoman / ABB / Staubli posts, 03.d KUKA, 03.b Fanuc `Go_Home` /
  `Weld`), and
  03.g (Fanuc) and 06.a (Mecademic) are not in the archive for the same reason.
* **After Update** (`tests/fixtures/robodk_gt/code/robodk_generated_code.tgz`, `dump_gt.py`): RoboDK had regenerated
  every machining project and simulated each program (`Item.Update`) before `MakeProgram`, so a target whose stored
  joints no longer reach its pose was written with the joints of RoboDK's simulation. The test replays this
  ("simulated" mode: the programs in RoboDK's order, the robot's joints chained from program to program, stale targets
  take the studio simulator's joints): **191 of 229 files are equal** (F2 measured 91 of 167 with the earlier harness).

The test lists each remaining difference with its reason and fails when a listed file becomes equal, so the table
below stays true. What RoboDK's generator does and the studio reproduces (each rule found in RoboDK's intermediate
files and covered by `tests/posts_rdk_job.test.ts` or the Library comparison):

* the joints stored with a target are handed to the post as they are, even when they no longer reach the target's pose
  exactly (01.c Home, 01.d InspectA 2); the configuration flags follow those joints (`confRLF`); IK runs only for a
  target without stored joints. After Update the stale targets carry the simulated branch instead
  (`CompileOptions.moveJoints`);
* numbers as RoboDK's posts receive them: joints and poses with 6 significant digits, poses as KUKA xyzabc
  (`posePP`), pose values below 1e-6 written as 0 (`src/posts/robopost.ts` `rdkPrecisionEvents`; the frozen post jobs
  and `python/post_shim.py` use the same rounding);
* a linear move to the point and orientation the previous move ended at (or with the same joints) is skipped
  ("Skipped move"), through the program and the sub-programs generated with it; a MoveJ and a MoveL that only turns the
  tool are kept (`dropZeroLengthMoves`, `PostProgram.skippedMoves`);
* a "Set reference frame" / "Set tool" is sent only when the pose changes (two tools with the same TCP are the same
  tool: 02.i keeps `///TOOL 45`); frame / tool ids are a number written as a word of its own in the name, -1 when there
  is none (06.f `Gripper1`), 0 for the robot's base frame (01.c);
* program names lose blanks and non-ASCII characters (05.b `Sıde0` → `Sde0.mod`); a Fanuc call keeps 8 (RJ3) / 12
  characters of the name while the file name keeps 6 / 10, like RoboDK (03.j MainProgram: `CALL PickEarC` for
  `PickEa.LS`; the post reports the mismatch);
* a "Start thread" reaches the post as the bare program name passed as code (`RunCode(name, False)`: UR `OpenGripper1`,
  ABB `RunConveyor`, 06.c-06.f);
* a robot on a synchronised rail / gantry: frames are stated w.r.t. the base of the axes that carry it, the post gets
  `dof` including the external axes and their types (`J` rotary / `L` linear); a frame on a synchronised positioner is
  stated w.r.t. the positioner flange together with `pose_turntable` (05.b, 05.c);
* a call of a program of another robot or mechanism (turntable `TT0deg`, RobotiQ `OpenGripper2`) is a call only, never
  the mechanism's joints posted as moves of the caller;
* Fanuc turn flags `ceil((j - 180) / 360)`; Motoman `///TOOL` keeps the last numbered tool and pulses are converted from
  the stored joints (zeros stay 0).

## RoboDK's built-in generators (robots without a post)

A robot whose station stores no post processor is generated by RoboDK.exe itself, not by a Python post. The studio
reproduces these generators in `src/posts/rdk_builtin.ts` and assigns them on import (`src/io/robodk/rdk_robot.ts`
`defaultPostOf`): `RoboDK_Builtin_ABB` (`.mod` with `rdkWObj` / `rdkTool` (mass 0.8 x the robot payload) /
`main_RoboDK`, external axes inline), `RoboDK_Builtin_KUKA` (`DEF`, `$BASE` / `$TOOL` blocks, `PTP` axis targets with
the flange comment), `RoboDK_Builtin_Fanuc` (`PR[10]` frames and tools, `MESSAGE` chunks), `RoboDK_Builtin_UR` (joint
moves, `set_tcp`), `RoboDK_Builtin_Comau` (`MOVE JOINT` / `MOVE LINEAR`, `$ROT_SPD` / `$LIN_SPD`; RoboDK's Comau
generator does not return on IO instructions, the studio reports them as problems) and `RoboDK_Builtin_Generic` (the
"Invalid license or undefined post processor" placeholder RoboDK writes for mechanisms).
`tests/posts_builtin.test.ts` compares each with the files RoboDK 5.9.4 wrote for feature programs added through
RoboDK's API to Library stations whose robot has no post (06.b ABB, 08.a KUKA, 06.d Fanuc + gripper, 07.e UR, 05.d
Comau on its gantry; `tests/fixtures/posts_gt/builtin/`, `make_builtin_gt.py`): the studio rebuilds the same programs
through its Robolink API and every file is equal. Other brands without a post are not verified against RoboDK's
built-in output.

## compileForPost

Targets are written relative to their frame (RoboDK `target.Pose()`); joints are the target's stored joints as they
are (a stale target is reported in `problems`), IK seeded with the current joints only for a target without stored
joints; RoboDK `conf_RLF` flags are attached; MoveC carries the via joints; per-move speed / rounding overrides become
explicit `setSpeed` / `setRounding` events; frames / tools are sent when they change (a program-level frame / tool,
which RoboDK has not, is stated before the first move); linear moves to the current point are skipped like RoboDK and
counted in `skippedMoves`, every other move is kept (unreachable targets are kept and reported); mechanisms (grippers,
turntables) move by their stored joints; calls to station programs passed as code are compiled as sub-programs;
"Start thread" is the bare name as code (`nativeThreads: true`: native thread events, a station script stays a
comment); analog outputs (RoboDK "Set AO", `io` with `analog: true`) become `setAO` events written in vendor syntax
(KUKA `$ANOUT[n]=v`, ABB `SetAO`, Fanuc `AO[n]=(v)`, UR `set_standard_analog_out`, Motoman `AOUT AO#(n) v`; other posts
fall back to their `setDO`). `tests/posts_library.test.ts`: every program of the 57 Library stations compiles in < 30 s,
keeps every move except the skipped ones and posts with its robot's post.

## Control flow (loop / if / thread / wait / signal)

Generated control programs (control-model code generation) use `loop`, `if`, `thread`, `wait` and `signal`
instructions. KUKA (FOR with a declared counter, LOOP, IF/ELSE), ABB (FOR / WHILE TRUE / IF), Fanuc (FOR R[], IF
THEN/ELSE, RUN), Motoman (label loop, `CALL JOB IF`), UR (counters, if/else, URScript threads), Kawasaki (FOR, IF SIG,
PCEXECUTE), Comau (FOR, IF, REPEAT) and Doosan (Python for / if) write them natively; other posts write a comment, call
the body once and report it (`tests/posts_control.test.ts`).

## RoboDK's original posts

* **Server** (`server/posts_native.ts`): `GET /posts/native` lists `C:/RoboDK/Posts` (env `ROBODK_POSTS`),
  `POST /posts/native/run {post, job, source?}` runs a RoboDK post (compiled or source, or a user post text) with
  RoboDK's embedded Python (env `ROBODK_PYTHON`) and returns every file (`ProgSave` into a temporary folder; archives
  as base64). In the browser `src/posts/native_client.ts` (`setNativePostServer`, `registerNativePosts`) registers
  them as asynchronous posts `RDK_<name>`: the app does this when it is opened with `?server=ws://host:port`, so
  RoboDK's posts appear in the post selectors. A RoboDK post name the studio has no built-in post for resolves to its
  native post (robot files keep working). The server registers them for its own headless station too
  (`setLocalNativePosts`): `prog.MakeProgram()` of an API client (the official `robodk` package included) with
  `robot.setParam('PostProcessor', 'RDK_KUKA_KRC2')` runs RoboDK's post in-process.
* **Export dialog**: asynchronous posts (Python / native) go through `generateProgram` (`App.exportProgramAsync`),
  synchronous ones through `App.exportProgramChecked`; the dialog lists the compiler problems and the post's own
  warnings (`PostProgram.problems`) above the preview, and binary files (`encoding: 'base64'`) download as such.
  `Robolink.MakeProgram` uses the same `generateProgram` path.
* `tests/e2e/server.e2e.test.ts`: the built server, the official `robodk` package over the binary protocol, Library
  Example 01.b: `MakeProgram` with RoboDK's KUKA_KRC2 post (native) and with the built-in KUKA_KRC2 both equal the
  `DrillingPart.src` RoboDK 5.9.4 generated itself (`tests/fixtures/robodk_gt/code`).
* **Browser** (Pyodide, `python_post.ts`): only *source* posts can run there (RoboDK's compiled `libspp` modules are
  native Windows extensions). The in-browser `robodk.robolink` stub carries RoboDK's own constants
  (`officialConstants()` of `python/robodk/_official.py`: `INS_TYPE_MOVE = 0`, `INS_TYPE_CODE = 8`, ...). The job goes through `post_shim.run_job_source` (sub-programs, `ProgSave`, all files,
  post log); imported post files are written next to each other so sibling imports work. `Program › Import RoboDK post
  processors` classifies the files: source posts -> Pyodide, compiled wrappers -> server posts (or skipped with a note
  when no server is configured). All 151 posts of RoboDK 5.9.4 are classified.
* `python/post_shim.py` keeps the files when a post writes them and only then needs the RoboDK API, and reports
  callbacks a minimal post does not define instead of aborting.

## Program importers (`src/io/programs/import.ts`)

KRL `.src` + `.dat` (typed / plain aggregates, `E6POS` / `E6AXIS` / `FDAT`, `$BASE` / `$TOOL`, `BASE_DATA` /
`TOOL_DATA`, `C_DIS`, `E1..E6`, RoboDK timer waits, messages, named outputs, companion `.src` sub-programs), RAPID
(every PROC as a program with calls, `Offs` / `RelTool`, zones, speeddata, tooldata / wobjdata as tools / frames,
`\MaxTime`), Fanuc LS (continuation lines = MoveC, UFRAME / UTOOL from `PR[]` writes and RoboDK's `! UFn:` comments,
WAIT TIMEOUT blocks, cm/min and inch/min, Arc Start / End), URScript (sub-program defs and calls, `movej` speed in rad/s
-> joint speed, `pose_trans(ref_frame, ...)`, `set_tcp`, `movec`, threads, IO ranges, while-waits), RoboDK CSV.
`tests/posts_import.test.ts` re-imports RoboDK's own outputs (KUKA, ABB, Fanuc R30i / RJ3, UR, CSV) and finds every
move with the same joints / poses in the same frames, plus Library `KUKA_Cutting.src` (1 PTP + 159 LIN in its `$BASE`).

G-code: R-format arcs, inch feeds converted; **APT / CL data** (`.apt` and APT content in `.nc`): GOTO with 5-axis tool
axes (kept as curve normals for the machining generator), RAPID, FEDRAT, LOADTL, CIRCLE, GODLTA, continuation lines —
the Library's Bowl, Spherical Part, Chess Rook and Tour Eiffel programs give their tool paths (`tests/gcode.test.ts`).

## ROS 2 package post

`ROS2` writes a complete ament_python package (`package.xml`, `setup.py`, launch file) whose node executes the program
through `/<controller>/follow_joint_trajectory` (FollowJointTrajectory action, ros2_control), starting from the current
`/joint_states` (the first point's time is computed from the distance at the programmed joint speed), with MoveL /
MoveC sampled in Cartesian space and solved with the robot model, sub-programs inlined, pauses, IO (`ur_msgs/SetIO`)
and input waits between goals. `tests/posts_ros2.test.ts` checks the sampled line / arc geometry and, in WSL with ROS 2
Jazzy, runs `colcon build` and the node against a fake FollowJointTrajectory server (in one rclpy process: FastDDS does
not deliver between processes in that WSL).
